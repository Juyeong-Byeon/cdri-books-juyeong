# ADR-0003: 제출된 검색 조건과 TanStack Query 기반 무한 스크롤

- **상태**: 승인 (Accepted)
- **결정·개정 일자**: 2026-10-24
- **결정자**: 변주영

## 배경

기획은 Enter로 검색을 확정하고, 결과를 페이지당 10개씩 무한 스크롤로 보여주도록 한다. 입력 중인 값이 확정 검색 조건을 바꾸거나, 이전 검색의 추가 페이지가 새 결과에 섞여서는 안 된다.

책의 제목·저자 등 도서 정보는 짧은 탐색 시간 안에 자주 갱신되지 않을 것으로 판단했다. 같은 조건으로 결과를 다시 읽거나 검색·찜 화면을 오갈 때마다 요청하기보다, 일정 시간 캐시를 재사용하는 쪽을 선택한다. 이는 도메인 특성에 대한 초기 판단이며 실제 갱신 주기를 측정한 결과는 아니다.

## 결정

- 서버 상태는 TanStack Query v5의 `useInfiniteQuery`에서 관리한다. 결과를 Zustand나 별도 로컬 상태에 복사하지 않는다.
- 검색은 Enter 또는 명시적인 검색 제출 동작으로 시작한다. 타이핑에 따른 자동 검색과 디바운싱은 도입하지 않는다.
- 검색 기록 선택도 제출 동작으로 취급한다. 전체·상세검색은 동시에 적용하지 않는다.
- 확정 검색 조건은 [ADR-0010](./0010-url-search-state-and-history.md)의 URL에서 읽고, 입력 중인 값은 로컬 상태로 둔다.
- 쿼리 키는 도서 도메인 접두사와 정규화된 확정 검색 조건으로 구성한다. 구체적인 배열 형태는 [getBookSearchQueryKey](../../src/pages/search/utils/bookSearchQueryKey.ts)에서 관리한다.
- 첫 페이지는 1, 페이지 크기는 10으로 요청한다. 페이지 번호는 쿼리 키와 URL에 넣지 않고 `pageParam`으로 관리한다.
- 검색어가 비어 있으면 쿼리를 비활성화한다. 검색 전 상태와 검색 성공 후 빈 결과를 구분한다.
- `getNextPageParam`은 매핑된 페이지의 `meta.isEnd`, 빈 도서 목록, API의 허용 페이지 범위를 기준으로 종료한다.
- 추가 요청 가능 여부는 `useBookSearch`의 `canLoadMore`와 `loadMore`에서 결정한다. 실패 후에는 관찰만으로 반복 요청하지 않고 재시도 UI를 제공한다.
- 교차 감지는 `useIntersectionObserver`가 맡고, 관찰 활성화·콜백·여유 범위는 `SearchResults`에서 옵션으로 전달한다. 교차 감지 훅은 Query와 도서 데이터에 의존하지 않는다.
- 쿼리의 `AbortSignal`을 HTTP 요청에 전달한다. 조건 변경 시 새 쿼리 키를 사용하고 기존 페이지를 새 결과에 합치지 않는다.
- 동일 식별자의 중복 문서는 목록을 구성하는 단계에서 정리한다.

### 공통 쿼리 설정과 선택 이유

앱에서 명시적으로 바꾼 기본 설정과 재시도 함수는 [RootProvider](../../src/providers/RootProvider.tsx)에서 관리한다. 수치와 조건을 문서에 별도로 복사하지 않고, 여기에는 선택 이유와 라이브러리 기본값을 유지한 범위를 기록한다.

| 설정                   | 선택 이유                                                                                                                                                                                                                                                             |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `staleTime`            | 도서 정보의 변경 빈도가 낮을 것으로 보고, 라이브러리의 즉시 stale 처리보다 신선도 유지 기간을 늘린다. 짧은 시간 안에 같은 검색으로 돌아올 때 캐시를 재사용해 요청과 로딩 전환을 줄인다.                                                                               |
| `refetchOnWindowFocus` | 창에 다시 포커스했다는 이유만으로 검색 목록을 재조회하지 않는다. 구매 링크를 새 탭으로 열고 돌아오는 흐름에서도 읽던 결과를 유지하며, 갱신은 검색 제출과 아래의 수명주기 정책으로 처리한다.                                                                           |
| `retry`                | 인증·검색 조건·요청 제한처럼 같은 요청을 반복해도 해결되지 않는 실패와 일시적인 연결·서버 실패를 구분한다. 자동 반복으로 인한 대기와 API 요청 소비를 제한하며, 세부 기준은 [ADR-0011의 재시도 정책](./0011-query-errors-and-render-boundary.md#재시도-정책)을 따른다. |

다음 설정은 별도로 덮어쓰지 않고 TanStack Query의 기본 동작을 사용한다.

- `gcTime`: 비활성 쿼리를 일정 시간 보관한 뒤 정리한다. 잠깐 다른 화면을 방문한 뒤 돌아오는 흐름은 지원하면서, 사용하지 않는 검색 결과를 무기한 메모리에 남기지 않기 위해 기본 보관 정책을 유지한다.
- `refetchOnMount`·`refetchOnReconnect`: 유효한 쿼리가 다시 마운트되거나 네트워크가 복구됐을 때, 데이터가 stale이면 재조회하는 기본 정책을 유지한다. 신선한 캐시를 재사용하면서 오래된 결과를 갱신할 기회를 남긴다.
- `retryDelay`: 라이브러리의 기본 백오프를 사용하고 별도의 재시도 타이머를 만들지 않는다.
- `refetchInterval`: 사용자가 조건을 제출해 결과를 탐색하는 흐름이므로, 사용자 탐색과 수명주기에 따른 갱신으로 충분하다고 판단한다. 주기적인 폴링은 사용하지 않는다.
- `structuralSharing`: JSON으로 표현 가능한 도서 데이터에서 동일한 부분의 참조를 재사용하는 기본 동작을 유지해, 카드와 파생 목록의 불필요한 변경을 줄인다.

`staleTime`은 데이터를 신선하게 보는 기간이고, `gcTime`은 사용하지 않는 캐시를 정리하는 기준이다. 이번에 도서 정보의 낮은 갱신 빈도를 근거로 늘린 것은 `staleTime`이며, `gcTime`을 별도로 늘린 것은 아니다. stale 전환 자체가 즉시 요청이나 삭제를 발생시키는 타이머는 아니다. 명시적인 같은 조건 재검색은 신선도와 관계없이 [useSearchSubmit](../../src/pages/search/hooks/useSearchSubmit.ts)에서 활성 쿼리를 갱신한다.

기본 동작의 의미는 [TanStack Query의 Important Defaults](https://tanstack.com/query/latest/docs/framework/react/guides/important-defaults)와 [useQuery 옵션](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery)을 따른다.

### 쿼리 키의 계층과 선택 이유

- 첫 요소는 도서 도메인을 나타내는 베이스 키로 둔다. 같은 도메인의 캐시를 접두사로 묶어 선택할 수 있는 경계를 만든다.
- 그 아래에는 확정 검색어·검색 대상·정렬을 하나의 조건 객체로 둔다. 결과를 바꾸는 조건이 다르면 별도 캐시를 사용하고, 같은 조건으로 돌아오면 이전 결과를 재사용한다.
- 입력 중인 값, 검색 기록 팝업의 상태, 현재 검색·찜 화면은 키에 넣지 않는다. 이 값들은 서버에서 가져올 도서 목록의 정체성을 바꾸지 않기 때문이다.
- 페이지 번호는 같은 검색의 누적 결과 안에서 `pageParam`으로 관리한다. 페이지별로 쿼리 키를 나누면 하나의 무한 스크롤 결과를 여러 캐시로 분산해 직접 합쳐야 하므로 `useInfiniteQuery`에 맡긴다.
- 페이지 크기는 현재 고정된 요청 정책이므로 키에 별도로 넣지 않는다. 향후 사용자가 페이지 크기를 바꿀 수 있게 되면, 결과 구성을 바꾸는 조건으로 키에도 포함해야 한다.
- 조회 훅과 동일 조건 재검색은 같은 키 생성 함수를 사용한다. 각 사용처에서 배열을 직접 조합하는 규칙을 중복 관리하지 않는다.

TanStack Query는 키를 내용에 따라 결정적으로 해시하므로, 같은 조건 객체를 매번 새로 만들었다는 이유만으로 별도의 캐시가 생기지 않는다. 문자열을 직접 이어 붙이는 별도 직렬화 규칙을 만들지 않는다. [공식 쿼리 키 안내](https://tanstack.com/query/latest/docs/framework/react/guides/query-keys)

## 대안과 선택 이유

| 대안                                   | 평가                                                                     |
| -------------------------------------- | ------------------------------------------------------------------------ |
| useEffect와 수동 페이지 상태           | 취소·캐시·오류·누적 결과를 직접 관리해야 하며 필수 기술 활용도 제한된다. |
| 입력 디바운싱 검색                     | 자동 검색에는 적합하지만 이번 Enter 제출 흐름과 다르다.                  |
| TanStack Query와 제출 기반 검색 (선택) | 요청 수명과 페이지 누적을 라이브러리에 맡기면서 기획을 따른다.           |

## 결과와 트레이드오프

캐시가 남아 있으면 같은 조건의 결과를 재사용할 수 있다. 캐시 유지 시간과 데이터의 신선도에 따라 재요청이 가능하므로 탭 복귀 시 요청이 항상 0회라고 보장하지 않는다. `staleTime`과 `gcTime`의 역할을 구분한다.

캐시를 재사용하는 동안 판매가·판매 상태의 변경이 바로 반영되지 않을 수 있다. 도서 정보가 완전히 불변이라고 가정하지 않고, 명시적인 재검색과 stale 상태의 마운트·재연결에서 갱신할 수 있도록 한다. 실시간 가격·재고 반영이 요구되는 화면으로 범위가 바뀌면 신선도 정책도 다시 결정한다.

무한 스크롤 위치와 로드한 페이지 수는 새로고침 시 복원을 보장하지 않는다. URL 조건으로 다시 검색할 수 있어야 한다.

## 구현 시 확인

입력만으로 요청하지 않음, 전체·상세 조건 전환, 요청당 10개, 중복 추가 요청 방지, 마지막 페이지 종료, 조건 변경 시 페이지 분리, 초기·추가 페이지 오류 복구를 [ADR-0012](./0012-testing-and-deployment-validation.md)에 따라 검증한다.
